# Scenario → Motion Graphics (Notion-driven b-roll pipeline)

Читает сценарий рилза из таблицы в Notion и под каждую помеченную строку (любой маркер, начинающийся с «бролл») генерирует отдельную Remotion-композицию в `src/animations/<slug>-<NN>-<mode>/`. Тип по умолчанию — половина; полный экран — только по явному «бролл фулл». Цель — синхронная визуализация: пока ведущий произносит конкретную реплику, на экране стоит моушн, который усиливает смысл этой реплики. Скилл заточен под репозиторий `reels/` и его конвенции.

## Where the scenario lives

Сценарий — это таблица в Notion (database или simple table) со строго двумя колонками:

| Левая колонка (текст) | Правая колонка (метка) |
|---|---|
| `https://www.instagram.com/reel/<id>/ • заголовок ролика` | — (пусто) |
| Полная фраза, которую ведущий произносит | пусто / `бролл` / `бролл половина` / `бролл фулл` |
| Следующая реплика | пусто / `бролл` / `бролл половина` / `бролл фулл` |
| … | … |

- **Одна строка таблицы = одна реплика** (1 мысль, 7–12 слов).
- **Первая строка** обычно содержит ссылку на референсный рилз + заголовок — это шапка, мы её не визуализируем.
- **Правая колонка может быть пустой**: это значит «здесь в видео будет крупный план ведущего, графика не нужна» — такие строки **пропускаем**.
- **Метки** (важно — слово `бролл` без опечаток; тип — опциональное слово после него):
  - `бролл половина` **или просто `бролл`** без указания типа → **half-top моушн 1080×1920 с графикой только в верхней половине** (это дефолт). В монтаже нижняя половина перекрывается лицом ведущего. Это основной тип серии — большинство визуализаций половинные, поэтому слово «половина» можно не писать: голый `бролл` уже означает половину.
  - `бролл фулл` (алиас `бролл full`) → **full-screen моушн 1080×1920**, кадр без лица ведущего. Полный тип теперь требует явного слова — без него получится половина.
- Допускаются вариации с лишними пробелами (`бролл  половина`, `бролл  фулл`) и регистром — нормализуй перед сравнением: trim + lowercase + collapse-spaces.
- **После метки может идти дополнительная инструкция к визуалу** — обычно в скобках, иногда без. Примеры:
  - `бролл половина (прозрачный фон и квадратами появляются различные mcp с лого друг за другом. Сами блоки в светлом стиле)` — явная половина.
  - `бролл (большая цифра 5 по центру, terracotta glow)` — тип не указан → половина по дефолту, хвост — это инструкция.
  - `бролл фулл (большая цифра 5 на весь экран, terracotta glow)` — полный экран.
  - `бролл половина — список с галочками появляется построчно`.
- Эта дополнительная инструкция — **обязательное требование к визуалу для этой конкретной строки**, она перебивает архетип, который ты выбрал бы по умолчанию. Если инструкция уточняет палитру/композицию/анимацию — следуй ей, даже если она расходится со style intake серии (style intake задаёт дефолт, per-row override его перекрывает).
- Парсинг: после нормализации `marker.toLowerCase().trim().replace(/\s+/g,' ')` строка должна начинаться с `бролл`. Дальше смотри на слово сразу после `бролл`: `фулл`/`full` → mode `full`; `половина` → mode `half`; **что угодно другое (включая пустоту, открывающую скобку или сразу текст описания) → mode `half` по дефолту**. Всё, что осталось после распознанного слова-типа (а в дефолтном случае — сразу после `бролл`), — это `extraInstructions: string | null`. Скобки и тире-разделители из инструкции вычисти: `extra.replace(/^[\s(\-—–]+/, '').replace(/[\s)]+$/, '')`.
- Если маркер непустой, но **не** начинается с `бролл` — спроси пользователя, что это значит, не угадывай.
- **Комментарий Notion на строке — ещё один канал указаний.** Пользователь может выделить текст в ячейке (обычно ячейку с меткой) и оставить комментарий: текст комментария — описание анимации, а вложения-изображения — **визуальные референсы** того, как должна выглядеть сцена. Если на помеченной строке есть комментарий — его **обязательно** считать и реализовать сцену на его основе (механика чтения, привязка к строке, фолбэки — `references/notion-comments.md`).
  - Вложения-изображения по умолчанию — _референс стиля/композиции_: воспроизводишь похожее **кодом** (Visual quality rule 5), файл в композицию не кладёшь. Картинка вставляется ассетом как есть только если в тексте явно сказано «вставь / используй как фон / как есть» (см. `references/external-assets.md`).
  - Текст комментария объединяется с инструкцией из маркера в общий `extraInstructions`; при прямом противоречии комментарий приоритетнее (он обычно создаётся позже и детальнее).
  - Комментарии на непомеченных строках — рабочие заметки, игнорируй: бролл по ним не делаем.

## When this skill triggers

- Пользователь даёт ссылку на Notion-страницу и просит сделать бролы/моушн/графику.
- Пользователь упоминает «таблица в Notion со сценарием рилза», «по моему сценарию из ноушна сделай моушн».
- Пользователь вызывает `/script-to-motion <notion-url>` (опционально + номер таблицы).

## When this skill does NOT trigger

- Сценарий вставлен текстом прямо в чат, без Notion-ссылки → попроси перенести в Notion-таблицу с колонкой меток (мы работаем строго по этому источнику).
- Правка уже сгенерированных композиций в `src/animations/...` — это обычный код-эдит, не запуск пайплайна.
- Чисто Remotion/React вопросы без сценария.
- Задачи рендера/билда (`npm run render`, `npm run build`).

## Inputs (что нужно получить до запуска)

1. **Notion URL** или ID страницы. Если не передан — спроси.
2. **Номер таблицы** на странице. По умолчанию — `1` (первая таблица сверху). Если на странице одна таблица — не спрашивай.
3. **(Опционально) базовый slug** для имён композиций. Если не передан — авто-генерируется из заголовка страницы или первой ячейки шапки.

## Project conventions (must respect)

- **Папка = композиция**: каждая анимация — отдельная папка `src/animations/<slug>/`. Имя папки = `id` в `defineAnimation` (kebab-case). Для одного сценария мы создаём **много папок** — по одной на каждый помеченный бролл.
- **Авто-регистрация**: `src/Root.tsx` подхватывает все `animations/*/index.{ts,tsx}`. Не редактируй `Root.tsx`. Вложенные подпапки внутри композиции игнорируются.
- **Контракт `defineAnimation`**: `export default defineAnimation({ id, component, durationInFrames, fps, width, height })`. Только default export, иначе `Root.tsx` бросит ошибку.
- **Уникальность `id`**: дубликат → `Root.tsx` бросает на старте. Перед записью — `ls src/animations/`, при коллизии добавь дисамбигуатор.
- **Канвас**: обе моды — **1080×1920 @ 30 fps**. Разница не в размере композиции, а в зоне отрисовки графики:
  - `бролл фулл` (full) → графика по всему канвасу 1080×1920, кадр без лица ведущего.
  - `бролл` / `бролл половина` (half, дефолт) → канвас тот же 1080×1920, но графика **только в верхней половине** `[0, 960]`; нижняя половина — тот же фон без графики, в монтаже её перекрывает лицо ведущего. Это НЕ композиция 1080×960 — детали в секции «Half-top safe zone».
- **Стек**: чистый Remotion — `interpolate`, `spring`, `useCurrentFrame`, `useVideoConfig`, `AbsoluteFill`, `Sequence`. Без Framer Motion / GSAP / animejs.
- **Шрифты**: по умолчанию `system-ui, -apple-system, sans-serif`. Кастомные — через `@remotion/google-fonts`, и только если пакет уже установлен.
- **Образцы**: `src/animations/hello-world/` (минимум), `src/animations/cloud-codes-skill-off/` (с вынесенными `LAYOUT`/`TIMING`/data), `src/animations/mcp-five-servers/` (мульти-сцены через `<Sequence>` + кастомная палитра).

## Autonomy (режим по умолчанию)

**Скилл работает автономно и ничего не согласовывает с пользователем, если пользователь явно об этом не попросил.** На входе достаточно двух вещей: ссылки на Notion-страницу и понимания, для какого видео делается визуализация. Всё остальное — стиль, палитру, шрифт, архетипы, длительности, storyboard — скилл решает **сам** и сразу запускает сборку. Не задавай вопросов ради одобрения, не жди «согласовано», не предлагай выбрать между вариантами — выбирай тот стиль/тему, который сам считаешь наилучшим и рекомендованным для этой серии.

- **Никаких approval-гейтов.** Storyboard и style intake — это твои внутренние решения; ты показываешь их пользователю как прозрачность (чтобы он видел, что делаешь), но **не останавливаешься и не ждёшь ответа** — сразу идёшь дальше.
- **Единственное исключение — реальные блокеры,** когда продолжить физически нельзя: не дана ссылка на Notion; структура таблицы не парсится (три колонки, объединённые ячейки); непустой маркер не начинается с `бролл`. Тогда — короткий вопрос, потому что угадать нечего. Это не «согласование», а разблокировка.
- Если пользователь **явно** просит «покажи план перед сборкой», «сначала согласуй стиль», «дай выбрать палитру» — тогда и только тогда включай соответствующие вопросы. По умолчанию их нет.

## Workflow

Когда скилл сработал, пройди фазы по порядку. Storyboard составляется всегда (это защита от не-того моушна), но он **не требует одобрения** — ты составляешь его сам и сразу переходишь к сборке.

### Phase 0 — Получить inputs

Нужны только два входа: **Notion URL** и понимание, для какого видео визуализация.

- Если **URL не дан** — это единственный жёсткий стоп на этой фазе: без него дальше не идём, коротко попроси ссылку.
- **Номер таблицы не спрашивай.** Если таблиц несколько — выбери ту, что соответствует видео (по заголовку/шапке/контексту запроса); при равной неоднозначности бери первую сверху и просто упомяни это в summary. Не устраивай `AskUserQuestion` ради выбора таблицы.
- **Slug не спрашивай** — авто-генерируй из заголовка страницы или первой ячейки шапки.

### Phase 1 — Прочитать таблицу из Notion (MCP)

Используй `mcp__claude_ai_Notion__notion-fetch` c URL/ID страницы. На странице найди указанную таблицу (database или simple table block). Если страница содержит database — fetch'и её data-source, получи rows. Если simple table — пройдись по `table_row` блокам.

Извлеки строки в виде `Array<{ text: string; marker: string | null }>`, в порядке появления в таблице. Не доверяй разметке колонок — определяй левую/правую по позиции/индексу ячейки в строке.

Кроме содержимого таблицы достань **комментарии строк**: пользователь может комментировать ячейки помеченных строк — текст комментария описывает анимацию, вложения-изображения служат визуальными референсами. Стратегия получения, привязка комментария к строке и фолбэки — `references/notion-comments.md`. Для каждой помеченной строки нужно знать: есть ли на ней комментарий, его текст и вложения-изображения. **Важно: текст и файлы вложений — это два разных канала.** Текст комментариев и маркеры даёт hosted-коннектор Notion (`notion-fetch`/`notion-get-comments`), но **сами файлы вложений он не отдаёт** — их качает локальный MCP `notion-comment-files` (`get_comment_attachments` по `page_url` или `block_ids` помеченных строк); в манифесте `saved_path` уже скачан на диск. Если у строки `image-attached-count ≥ 1`, без этого инструмента референса не получить — детали и фолбэк в `references/notion-comments.md`.

Если что-то не парсится (нестандартная структура, три колонки, объединённые ячейки) — **остановись и спроси пользователя**, не угадывай.

### Phase 2 — Распарсить и отфильтровать

1. Нормализуй `marker`: `String(marker).trim().toLowerCase().replace(/\s+/g, ' ')`.
2. Классификация. Сначала отсей пустые: пусто или `null` → пропустить строку. Непустой маркер **обязан** начинаться с `бролл`, иначе → **спроси у пользователя**, прежде чем продолжать. Дальше — по слову сразу после `бролл`:
   - `фулл` или `full` → mode `full`. Хвост после этого слова — `extraInstructions`.
   - `половина` → mode `half-top`. Хвост после этого слова — `extraInstructions`.
   - **всё остальное — пусто, открывающая скобка или сразу текст описания → mode `half-top` по дефолту.** Тип не указан = половина (большинство визуализаций серии половинные). Хвост — это всё, что идёт после самого слова `бролл`, — `extraInstructions`.
3. **Извлеки токены внешних ассетов** из хвоста маркера (до творческого текста): `фон:<file>`, `оверлей:<file>`, `фото:<file>`. Их может быть несколько, в любом порядке. Тип ассета определяй по расширению (`.mp4/.mov/.webm` → видео, `.jpg/.png/.webp` → картинка). Запомни ожидаемый путь `public/assets/<slug-NN>/<file>`. Полная грамматика и форматы — `references/external-assets.md`. То, что осталось после меток и токенов, — это `extraInstructions`.
4. **Очисти `extraInstructions`**: убери открывающие/закрывающие скобки, тире-разделители, пробелы. `extra.replace(/^[\s(\-—–:]+/, '').replace(/[\s)]+$/, '')`. Если после очистки строка пустая — `extraInstructions = null`.
5. **Подмешай комментарий строки** (если есть, см. `references/notion-comments.md`): текст комментария добавь к `extraInstructions` (инструкция маркера + комментарий — оба обязательны; при прямом противоречии комментарий приоритетнее). Вложения-изображения комментария собери в **`referenceImages`** с ролью каждого: по умолчанию `референс` (воспроизводим кодом), `ассет` — только если в тексте явно сказано вставить как есть. Сами файлы берёшь из манифеста `notion-comment-files` (`saved_path` — уже скачаны); запомни путь каждого, финальные пути под slug серии разложишь в Phase 5.1.
6. Сформируй финальный список `B-rolls`: каждый элемент содержит порядковый номер (по порядку среди помеченных, не среди всех строк), исходный индекс строки в таблице, текст реплики, mode, **extraInstructions** (или null), **referenceImages** — список `{ path, role: 'референс'|'ассет' }` (или пустой) и **assets** — список `{ kind: 'фон'|'оверлей'|'фото', file }` (или пустой).
7. Сразу посчитай длительность каждого бролла (см. секцию «Pacing»).

Покажи пользователю короткое summary первой фазы — сколько броллов нашёл, какие full / половина, сколько строк несут комментарии с референсами, общее экранное время — **до** style intake. Это даёт шанс заметить ошибку парсинга на ранней стадии.

### Phase 3 — Style intake (ты решаешь сам, 1 раз, общий на всю серию)

**Не спрашивай пользователя.** Стиль серии — базовый slug, палитру, шрифт, accent-цвет — выбери сам, исходя из темы видео, тона сценария и того, что смотрится сильнее всего. `references/style-intake.md` используй как справочник хороших дефолтов и палитр — не как список вопросов. Длительность не выбирается, она считается.

Критерии выбора (сам, без согласования):
- **Палитра** — под тему и настроение ролика (тёмная тех-палитра для про-разработку/ИИ, светлая для продуктовых/лайфстайл, terracotta-акцент как узнаваемый бренд-акцент серии, если уместно). Бери ту, что сам считаешь наилучшей.
- **Шрифт** — системный `system-ui` по умолчанию; кастомный из `@remotion/google-fonts` только если пакет уже установлен и он явно усиливает стиль.
- **Slug** — авто из заголовка страницы/шапки.

Выбранный стиль применяется ко всем броллам в серии: палитра, шрифт, accent-цвет — общие, чтобы серия выглядела как один ролик. Кратко озвучь пользователю, какой стиль выбрал (одна строка — прозрачность), и сразу иди дальше. Спрашивай про стиль **только если пользователь явно попросил дать ему выбрать**.

### Phase 4 — Storyboard (по одной строке на бролл)

Выдай нумерованный список **только помеченных** строк в следующем формате:

```
Сценарий: «Как использовать Claude Code бесплатно» (slug базы: claude-code-free)
Найдено броллов: 9 (половинных: 7, полных: 2)
Общая длительность графики: ~38 сек

Storyboard:
 #01  [half-top, 90f / 3.0s]  big-number  «Раньше нужно было платить минимум 20 долларов»
       Half-canvas 1080×1920, графика только в top [0, 960]. На экране: огромная цифра $20 с зачёркиванием накрест, подпись «раньше».
       Slug: claude-code-free-01-half

 #02  [half-top, 120f / 4.0s]  callout-quote  «и этой подписки хватало на очень маленькое количество запросов»
       Half-canvas 1080×1920, графика только в top [0, 960]. На экране: иконка истощённой батарейки + крупный текст «мало запросов».
       Slug: claude-code-free-02-half

 #03  [full, 135f / 4.5s]  diagram  «но теперь его можно запускать, используя локальные open source модели»  ← маркер: «бролл фулл»
       Полный канвас 1080×1920. На экране: ноут с локальным процессом, надписи «локально», «open source», стрелка к Claude Code.
       Slug: claude-code-free-03-full

 #04  [half-top, 75f / 2.5s]  key-statement  «от Olama, без каких-либо подписок»
       Half-canvas 1080×1920, графика только в top [0, 960]. На экране: лого-имя «Ollama» + крест на «$».
       Slug: claude-code-free-04-half

 …
```

Правила формата:
- Покажи **все** помеченные строки, в исходном порядке, с номером, точной репликой, архетипом (из `references/visual-archetypes.md`), длительностью в кадрах и секундах, slug'ом и кратким описанием визуала.
- Архетип выбирай по **форме высказывания**: число → big-number, «раньше/теперь» → before-after, перечисление → bullet-stagger, определение → key-statement, процесс → diagram-with-arrows, технический сниппет → code-block.
- **Если у строки есть `extraInstructions` (доп. инструкция в маркере и/или комментарий Notion)** — она имеет приоритет над любым выбранным архетипом и над дефолтами style intake. Покажи её в storyboard'е отдельной строкой «**Указания пользователя:** <текст инструкции>», а описание визуала составь так, чтобы реализовывать эти указания буквально. Если инструкция противоречит палитре/шрифту серии (например, «прозрачный фон» при выбранной тёмной палитре) — следуй инструкции, серия может быть стилистически смешанной.
- **Если у строки есть `referenceImages` (вложения комментария Notion)** — открой каждое изображение через `Read` **до** составления описания визуала: storyboard-описание должно строиться на референсе. Покажи в storyboard'е строкой «**Референс:** N изображений» и кратко, что именно берёшь из каждого (композиция / палитра / персонаж / конкретный объект), с ролью: `референс` (рисуем кодом) или `ассет` (вставляем файлом).
- Если для конкретной сцены нужен **мелкий текст** (например, ввод команды в терминал, выбор пункта в UI) — **явно отметь это в storyboard'е** строкой «требует мелкого текста (терминал/UI)». Отдельного подтверждения не проси — просто реализуй по правилу 2 из «Visual quality rules» (моноширинный шрифт, контрастная подложка, типизация посимвольно). Пометка нужна для прозрачности, а не как гейт.
- **Если у строки есть внешние ассеты** (токены `фон:`/`оверлей:`/`фото:`) — покажи их строкой «**Ассеты:** фон=city.mp4, оверлей=sparks.webm» и опиши, как они лягут слоями (фон → ассет → код-графика → субтитры). Если файла ещё нет в `public/assets/<slug-NN>/` — пометь «(нужен файл, будет бриф)».
- Для `half-top` явно укажи `Half-canvas 1080×1920, графика только в top [0, 960]` — напоминание для тебя самого, чтобы потом не залезть координатами в нижнюю зону.

Storyboard — это твой план, **а не запрос на одобрение.** Покажи его пользователю для прозрачности и **сразу переходи к Phase 5** (пишешь файлы, спавнишь субагентов) — не заканчивай вопросом, не жди «согласовано». Единственное, что может остановить тебя здесь, — реальный блокер парсинга из Phase 1/2 (нераспознанный маркер, неразбираемая таблица). Если пользователь **явно** просил показать план до сборки — только тогда останавливайся и жди ответа; иначе иди дальше сам.

### Phase 5 — Сгенерировать файлы (параллельно, по субагенту на бролл)

Как только storyboard составлен (без ожидания одобрения), монтаж броллов распараллеливается: **каждый бролл собирает отдельный субагент**. Это безопасно, потому что броллы изолированы — каждый живёт в своей папке `src/animations/<slug>-<NN>-<full|half>/`, имена уникальны и зафиксированы в storyboard, общего мутируемого состояния между ними нет. Параллельная сборка экономит и время, и контекст оркестратора (серия может быть 30+ броллов).

Порядок ровно такой — не меняй его, шаги 5.1 и 5.3 обязаны быть последовательными вокруг параллельного 5.2:

#### 5.1 — Создай общую тему серии (ты сам, до спавна субагентов)

Создай `src/shared/<slug>-theme.ts` с токенами серии: `COLORS`, `FONTS`, `FPS`, и half-хелперы (`HALF`, `halfBackground`, `halfTopZone`, `stage` — см. образец `src/shared/claude-5-day-guide-theme.ts`). Палитра/шрифт — из style intake (Phase 3).

Почему это делает главный агент и именно сейчас:
- **Единство стиля.** Тема — главный механизм связности серии: все броллы импортируют одни цвета/шрифт/safe-area, поэтому при параллельной независимой сборке серия не «расползается» визуально.
- **Защита от гонки.** Если бы тему создавали субагенты, несколько из них писали бы один файл одновременно — конфликт. Тема должна существовать **до** спавна, чтобы субагенты её только импортировали.
- Не клади тему в `src/animations/` — `Root.tsx` попытается её зарегистрировать и упадёт. Только `src/shared/`.

**Затем разложи картинки-референсы по финальным путям.** Субагент не видит вложения комментариев Notion из твоего контекста — он работает с файлами. Референсы из манифеста `notion-comment-files` (`saved_path`, скачаны в Phase 2) **скопируй** в `public/assets/<slug-NN>/ref-<K>.<ext>` соответствующего бролла (slug теперь известен из style intake). В спецификацию субагента пойдёт именно **путь к файлу** + роль (`референс` → воспроизводит кодом / `ассет` → вставляет файлом).

#### 5.2 — Спавн всех субагентов разом

Запускай субагентов (`Agent`, тип `general-purpose`) **все сразу, одним сообщением** — по одному вызову `Agent` на каждый бролл серии, без деления на батчи и без лимита на количество. Это безопасно и быстрее всего: броллы полностью изолированы (см. выше), общего мутируемого состояния между ними нет, поэтому ограничивать число одновременных субагентов незачем — чем больше идёт параллельно, тем быстрее собирается серия. Спавни столько вызовов `Agent`, сколько броллов в storyboard, в одном сообщении; если их окажется больше, чем харнесс готов крутить одновременно, лишние он сам поставит в очередь и подхватит по мере освобождения слотов. Промежуточных волн нет — просто дождись, пока завершатся все субагенты.

Каждому субагенту дай промпт со **спецификацией одного бролла** и укажи прочитать контракт. Шаблон промпта:

```
Ты собираешь ОДИН b-roll вертикальной серии. Сначала прочитай контракт:
<SKILL_DIR>/references/subagent-brief.md — следуй ему строго.

Спецификация бролла:
- slug: <base>-<NN>-<full|half>
- mode: full | half
- text: «<реплика ведущего>»
- archetype: <архетип из storyboard>
- durationInFrames: <N>, fps: 30
- visualDescription: <описание сцены из storyboard>
- extraInstructions: <текст per-row override (маркер + комментарий Notion) или null>
- referenceImages: <[{path: 'public/assets/<slug-NN>/ref-1.png', role: 'референс'|'ассет', note: <что брать>}] или нет>
- assets: <[{kind, file, path}] или нет>
- theme: импортируй из '../../shared/<base>-theme' (уже создана; экспортит COLORS, FONTS, FPS, HALF, halfBackground, halfTopZone, stage)
- paths: SKILL_DIR=<абсолютный путь к скиллу>, REPO_ROOT=<абсолютный путь к репозиторию>

Собери композицию в src/animations/<slug>/ и верни краткий отчёт в формате из контракта.
Картинки-референсы открывай через Read по их path. Не трогай ничего вне своей папки.
typecheck/studio не запускай — это сделаю я.
```

Подставляй конкретные значения из storyboard. `visualDescription`, `extraInstructions` и пути референсов передавай дословно — это ТЗ субагента.

#### 5.2.1 — Открыть редактор, как только готовы первые 5 броллов (не жди всю серию)

**Не дожидайся завершения всех субагентов, чтобы показать результат.** Как только завершились
**пять** субагентов (а если броллов в серии меньше пяти — то все), сразу запусти

```
node tools/open-editor.mjs <slug>
```

— тот же `<slug>`, что у темы серии в `src/shared/<slug>-theme.ts`. Studio поднимется (или
переиспользуется уже открытая), вкладка Chrome наведётся на первую готовую композицию серии,
в сайдбаре останется раскрытой только папка этой серии. Пользователь начинает работать с
видео, пока остальные броллы ещё собираются.

- Это **не финальный шаг, а ранний**: остальные субагенты продолжают работать параллельно,
  ты продолжаешь ждать их, ничего не отменяя.
- **Повторно скрипт запускать не нужно** — Remotion Studio подхватывает новые композиции
  сама (dev-server следит за `src/animations/*`), поэтому доехавшие позже броллы появятся
  в раскрытой папке серии без твоего участия.
- Typecheck на этот момент ещё не прогонялся — это нормально. Если недособранный бролл
  временно не компилируется, Studio покажет ошибку в этой композиции; на остальные она не
  влияет и блокером не является. Все ошибки чинятся централизованно в Phase 6.
- Скажи пользователю одной строкой, что редактор открыт и на скольких броллах из скольких
  (например: «Редактор открыт на серии — 5 из 12 готовы, остальные дособираются»).

#### 5.3 — Собери результаты

Когда все субагенты завершились, фиксируй их отчёты. Если субагент вернул ошибку (коллизия имени, нечитаемый референс, противоречивая спецификация) — разберись сам или переспаунь с уточнённой спецификацией. Соедини список созданных композиций для Phase 6.

### Phase 5.5 — Звук (ОТКЛЮЧЕНО по умолчанию)

**Звук в этот пайплайн больше не входит.** Не запускай `sounds-on-motion` сам и не считай
серию «неготовой» из-за отсутствия звуковых эффектов — наложение звука заметно удлиняет
сборку, а пользователю нужно быстрее получить готовую графику в редакторе.

- Серия считается готовой без звука. В финальном отчёте не пиши «осталось наложить звук» и
  не предлагай это как следующий шаг по умолчанию.
- Звук накладывается **только по явной просьбе пользователя** («наложи звук на бролл», «добавь
  звуки появления») — тогда запускается скилл `sounds-on-motion` в своём обычном режиме
  «по запросу на существующую композицию».
- Тайминги появления всё равно держи в `T` (см. ниже) — это дешёво и оставляет возможность
  озвучить серию позже одним проходом.

### Phase 6 — Verification (ты сам, один раз на всю серию)

Когда все субагенты завершены:

1. **Один `npm run typecheck`** на весь проект (read-only по эффекту, безопасно). Субагенты его не запускали — проверка централизована здесь, чтобы избежать шума от параллельных недописанных файлов. Все ошибки исправь сам до отчёта «готово».
2. **Лёгкий ревью-проход.** Бегло просмотри сгенерированные файлы (хотя бы выборочно по одному из каждого архетипа и все, где субагент в отчёте отметил риск) на соответствие нормативным правилам: half-top safe zone (графика только в `[0, 960]`), side padding, крупный текст, отсутствие дублирования смысла подписью, наличие движения, `clamp` в `interpolate`. Это компенсирует то, что каждый субагент видел только свой бролл, а не серию целиком. Расхождения — поправь.
3. **Редактор уже открыт с Phase 5.2.1 — повторно его дёргать не надо.** Studio подхватила доехавшие броллы сама. Запусти `node tools/open-editor.mjs <slug>` ещё раз **только** если Studio на шаге 5.2.1 не открылась (ошибка скрипта) или пользователь её закрыл. Пользователь **не должен** просить «открой редактор» вручную — открытие делается автоматически, просто раньше: не в конце, а на пятом готовом бролле. Что делает скрипт: поднимает Remotion Studio, если она не запущена, иначе переиспользует уже открытую (нового сервера не плодит), наводит вкладку Chrome на первую композицию серии и оставляет раскрытой в сайдбаре **только** папку этой серии — все ранее раскрытые папки сворачиваются.
   - **Механика (важно, не «само раскрывается по URL»):** состояние раскрытых папок Studio живёт в `localStorage['remotion.expandedFolders']` (ключ верхнеуровневой папки = `no-parent/<slug>`). Переход по URL `/<id>` композицию **выбирает**, но папку в сайдбаре **не раскрывает** и чужие не сворачивает — это проверено. Поэтому скрипт пишет это состояние через JS на странице Chrome (AppleScript `execute ... javascript`): ставит `expandedFolders` в ровно одну целевую папку и перезагружает вкладку. Заодно это чинит баг macOS, когда `open <url>` при уже открытой вкладке того же origin лишь активирует её, не переходя на новый путь.
   - **Разовая настройка Chrome:** для записи localStorage нужен включённый в Chrome пункт **View → Developer → Allow JavaScript from Apple Events** (хранится в подписанных Secure Preferences — программно не включить; в меню пункт может выглядеть серым, но `AXPress`/ручной клик его включает, иногда с подтверждением Return). Если он выключен, скрипт деградирует: просто наводит вкладку на нужную композицию (папка не раскроется/не свернётся) и печатает подсказку. Если у пользователя папка не открывается — почти наверняка выключена эта настройка.

В конце сообщи: общее число созданных композиций, как именованы (`<slug>-NN-mode`), путь к общей теме, что редактор открыт на папке серии, какие броллы ждут внешних ассетов (с путями briefs), и какой `npm run render <id>` нужен для конкретного бролла.

**Рендер раскладывается по сериям АВТОМАТИЧЕСКИ.** Каждая композиция в `src/Root.tsx` получает `calculateMetadata → defaultOutName = '<slug>/<id>'`, поэтому путь вывода по умолчанию = `out/<slug>/<id>.<ext>` (отдельный каталог на видео, как папка серии в сайдбаре; slug берётся ДО завершающего `-NN[-mode]`). Применяется И в CLI (`remotion render`, `npm run render`), И в Render-модале веб-Studio (панель «Renders») — путь совпадает везде, вручную вводить не надо; подпапку Remotion создаёт сам, контейнер по кодеку (`.mp4`, при ProRes → `.mov`). Обёртка `tools/render.mjs` — тонкое batch-проксирование: `npm run render -- <id1> <id2> …` рендерит несколько за раз, каждый в свою папку.

## Pacing rule (текст → кадры)

- **Темп речи**: 2.5 русских слова в секунду — типичный темп для рилз-нарратива.
- **Длительность одного бролла**: `seconds = max(2.0, words / 2.5 + 0.5)` (0.5с воздуха в конце, плюс минимум 2 секунды — даже короткая фраза должна успеть «прочитаться» зрителем).
- **Кадры**: `durationInFrames = Math.ceil(seconds * 30)`.
- **Хук**: если первый бролл — это начало ролика, ключевой визуал в первые 45 кадров. Если бролл стоит в середине сценария — это правило не применяется.
- **Воздух между броллами не нужен**: в реальном видео между ними часто идёт строка без пометки = крупный план лица. Композиция бролла должна быть «упакованной» под свою реплику.

## Visual quality rules (нормативные дефолты — держись их сам, не спрашивая)

Это жёсткие правила качества, а не предложения на согласование. Соблюдай их автономно; не останавливайся, чтобы спросить разрешения отступить — просто следуй им.

1. **Крупный текст и крупные иллюстрации в приоритете.** Заголовок реплики на экране — минимум 80px, обычно 120–240px. Подзаголовок — 30–48px. Надписи <26px не используй (кроме случая мелкого текста из правила 2).
2. **Мелкий текст — только внутри интерфейсной графики.** Уместен, когда сама графика — это набор текста в интерфейсе: терминал, поле ввода, чат. В этих случаях моноширинный шрифт, контрастная подложка, типизация через `interpolate` по символам. В storyboard'е такие сцены помечай явно (см. Phase 4), но отдельного подтверждения не проси — реализуй сам.
3. **Динамика обязательна.** Каждый бролл должен иметь видимое движение во всём своём диапазоне: entry-spring, фоновая пульсация, count-up, прорисовка стрелки, stagger карточек, hover-glow. Статичная картинка на 3 секунды = провал — зритель свайпает.
4. **Качество прорисовки.** Все элементы — на корректных координатах, без обрезаний; цвета согласованы (палитра из style intake); shadow/glow не дребезжит и не выходит за границы канваса; emoji-иконки рендерятся корректно (системные emoji в Chrome выглядят иначе, чем в финальном рендере — Remotion использует Skia, проверь в Studio).
5. **Иллюстрации, не клипарт.** Код-графику строй из геометрических форм, типографики, SVG-примитивов и emoji — **не** пытайся синтезировать растровые «настоящие» иллюстрации кодом, этого в Remotion нет. Если в storyboard'е написано «иконка ноутбука» — это «стилизованный SVG прямоугольник с экраном», а не PNG ноутбука. **Картинки-референсы из комментария Notion** воспроизводи кодом по мотивам (композиция, палитра, идея, персонаж), не пытайся скопировать пиксельно. **Исключение — внешние ассеты:** когда нужен фотореализм/текстура/отражения/органичный моушн, это берётся готовым файлом (AI-генерация или скачанный клип/фото) и кладётся слоем через примитивы `AssetVideo`/`AssetImage` (см. `references/external-assets.md`), а не рисуется кодом.
   - **Готовые лого/маскоты — из библиотеки исходников, НЕ рисуй кодом и не генерируй заново.** Если в кадре нужен узнаваемый бренд-знак или маскот (маскот Claude Code, инструменты, бренды, конкурирующие модели) — **сперва проверь общую библиотеку** `public/library/logos/**` (реестр происхождения — `public/library/manifest.json`): там уже лежат готовые прозрачные PNG. Раскладка: маскот Claude Code (терракотовый робот с `>` `<`) — `logos/anthropic/claude-logo.png`; бренды (Notion/GitHub/Figma/Slack/Gmail/Obsidian…) — `logos/brands/`; конкурирующие модели/инструменты (Kimi/GLM/Codex/Cursor…) — `logos/competitors/`; Google-инструменты — `logos/google/`. Нашёл — вставляй **файлом** через `lib()` + `<Img>` (для маскота Claude Code есть готовый компонент `<ClaudeCodeLogo>` в `src/shared/claude-code-logo.tsx`). **Нет в библиотеке** — досорсь настоящий лого (официальный сайт/favicon/apple-touch/пресс-кит/Wikimedia, фон выбей в прозрачность отдельным субагентом) и **положи в `public/library/logos/<вендор>/` + обнови manifest.json**, чтобы следующая серия переиспользовала. Рисовать пиксель-арт/SVG вручную допустимо только для generic-иконок без канонического бренд-знака (папка, шестерёнка, ноутбук, стрелка). Это же относится к любым переиспользуемым исходникам, а не только к лого: перед тем как строить с нуля — проверь, нет ли готового в `public/library/`.
6. **АВТОРСКИЕ НАДПИСИ — ПО-РУССКИ, ИНТЕРФЕЙС — КАК В ЖИЗНИ.** Аудитория русскоязычная, поэтому **любая надпись, которую пишешь ты как автор кадра, пишется на русском**: заголовок сцены, eyebrow-кикер над ним, подписи к элементам, поясняющие лейблы, чипы, tagline, подписи узлов схемы. Даже если картинка-референс от автора англоязычная — из неё берётся **композиция**, а надпись переводится. Референс — это макет, а не источник текста.
   - **НЕ переводится то, что изображает реальный интерфейс**: содержимое окна терминала (вывод команд, `Running tests…`, `Read 128 files`, `Error: usage limit reached`), Claude Code TUI, UI-панели продукта (`Claude Code — Free Plan`, `Tokens remaining`, `Out of tokens — upgrade to continue`, `connected`), строки автодополнения команд. Терминал по-русски выглядит фальшиво — зритель этой аудитории читает такие экраны как есть. Мелкий текст в интерфейсной графике вообще не несёт смысла реплики (см. правило 2), он создаёт фактуру.
   - **Никогда не переводятся:** названия брендов/продуктов/моделей (Claude Code, Gemini, Kimi, GLM, App Store, React Native, GitHub), команды и флаги (`/commit`, `/compact`, `git commit -m`, `npm install`), пути к файлам, код, технические токены (MIT, JSON, API, MB).
   - Примеры: `RUNNING CLAUDE CODE WITH` → «CLAUDE CODE РАБОТАЕТ» (авторский кикер), `∞ UNLIMITED USAGE` → «∞ БЕЗ ЛИМИТОВ» (авторский заголовок), `PROVIDERS` → «ПРОВАЙДЕРЫ» (авторский кикер); а `✳ Analyzing project structure…` и `tokens used: ∞ Unlimited` внутри окна терминала остаются английскими.
   - Граница простая: **это надпись от меня зрителю или это то, что написано на экране у героя?** Первое — русский, второе — оригинал.
   - Русский текст на 10–20% длиннее английского: после перевода проверь, что заголовок влезает в safe-area (контентная ширина 888px) и не переносится некрасиво — подбери формулировку или сбавь fontSize.
7. **Hook discipline для первого бролла серии.** Если самый первый бролл — это и есть хук ролика, ключевой визуал должен попасть в первые 45 кадров. Никаких «постепенно начинаем».
8. **Не дублируй визуализацию текстом.** Если графика уже исчерпывающе передаёт смысл реплики — подпись/tagline снизу **не нужна**, это шум. Пример: сцена с лупой, поисковой строкой и анимированным набором запроса — это уже «мощный поиск», подпись «мощный поиск» лишняя. Подпись уместна только когда она добавляет **новую** информацию (число, ключевое имя, новое уточнение). Эмпирическое правило: спроси себя «эту фразу зритель уже понял из графики за 2 секунды?» — если да, удали.

## Half-top safe zone

**Композиция half всегда 1080×1920** (как и full) — НЕ 1080×960. Под видео-монтаж нужны одинаковые таймлайны и одинаковое соотношение сторон; разные высоты у full/half плодят головную боль в редакторе.

- `index.ts` для half-бролла: `width: 1080, height: 1920` (так же, как full).
- **Фон композиции заполняет ВЕСЬ канвас 1080×1920** — никакой прозрачности. Прозрачная нижняя половина даст «дыру» в финальном mp4 (формат прозрачность не сохраняет) и испортит превью в Studio.
- **Графика** (текст, иллюстрации, анимированные элементы) отрисовывается **только в верхней половине** канваса: top `[0, 960]`. Нижняя половина `[960, 1920]` — **тот же фон, без графики**, потому что в монтаже она перекрывается лицом ведущего.
- Все интерактивные/значимые элементы — в зоне top `[60, 880]`. Между низом графики и линией `y=960` оставь воздух 40–80px, чтобы плавно подходить к стыку с лицом, без обрезаний.
- Никаких визуальных элементов в нижней половине: ни заголовков, ни иконок, ни glow, ни «полосы accent». Если хочется разделитель между половинами — клади его на координату `y=960`, а не у `y=1920`.
- Активные эффекты (pulse, radial-gradient, частицы) — **в обёртке с `overflow: hidden` и `height: 960`**, чтобы они не залезали в нижнюю половину, где это бессмысленно (под лицом ведущего) и грузит рендер.
- Фон-цвет/градиент в нижней половине должен быть **визуально однородным** — желательно плоский цвет или горизонтальный градиент (одинаковый по всей высоте). Вертикальный gradient растянутый на 1920 даст странное «второе изображение» снизу; если нужен вертикальный — ограничь его в обёртке верхней половины, а на всю композицию положи плоский цвет того же тона.
- Размер главного текста в half — на 20–30% меньше, чем в full (240px → 180–200px): по вертикали полезной зоны вдвое меньше, в неё нужно уместить заголовок + основную графику + подпись.

Это нормативно: half = 1080×1920, фон по всему канвасу, графика только в верхней половине. Не делай 1080×960 — это сломает монтаж. Не делай прозрачную нижнюю половину — это испортит превью и mp4.

## Side padding / safe area (Instagram Reels)

В Reels на мобильном экране **боковые ~80–100px частично перекрываются** UI (имя автора, кнопки лайка/комментариев, шторки). Под это правило все значимые элементы должны иметь горизонтальный safe-margin:

- **Side padding минимум 96px** с каждой стороны (≈9% от ширины 1080). Текст, аватарки, главные UI-элементы — в диапазоне `x: [96, 984]`.
- Декоративные слои (фоновый gradient, размытый glow) могут уходить за safe-area — но любой читаемый или значимый элемент — нет.
- **Контентная ширина** ≈ 888px. Текст и компоненты рассчитывай под неё, а не под полные 1080.
- В макетах с двумя колонками side-by-side (before-after, две карточки) — `padding: '0 96px'` на контейнер, `gap` между колонками ≥ 32px.
- Bottom safe area: оставляй 60–80px чистого пустого пространства снизу для full-broll (нижние строчки текста часто перекрываются caption'ом).

Это применимо к **full** и **half** одинаково. В half — safe-area считается от верхней половины (0–960), не от всей композиции.

## File structure conventions (per бролл)

- **Минимальный бролл** (1 экран, ≤120 строк tsx): `index.ts` + `Animation.tsx`. Всё inline.
- **Средний бролл** (1 экран, повторяющиеся под-элементы): `index.ts` + `Animation.tsx` + `Card.tsx` + `data.ts`.
- **Сложный бролл** (несколько внутренних под-сцен с разной композицией): `index.ts` + `Root.tsx` + по `Scene.tsx` на каждую под-сцену, склейка через `<Sequence>`. Образец — `src/animations/mcp-five-servers/McpFiveServers.tsx`.
- Запрещено: подпапки внутри композиции (бандлер их игнорирует).

### Тайминги появления держи в `T` (это точка стыковки со звуком)

Кадры появления элементов выноси в объект `T` в `data.ts` (`itemsFrom`, `itemStagger`,
`sendAt` …), а не разбрасывай литералами по `Animation.tsx`. Помимо читаемости это оставляет
серию озвучиваемой задним числом: скилл **`sounds-on-motion`** цепляет эффекты именно к `T`,
чтобы всплеск попадал на кадр появления элемента и уезжал вместе с ним при правке тайминга.
Сам звук в этом пайплайне **не накладывается** (Phase 5.5 отключена) — но если пользователь
попросит озвучить серию позже, вынесенные в `T` тайминги позволят сделать это одним проходом.

## Verification gotchas

- **Дубль `id`** → `Root.tsx` падает. `ls src/animations/` перед записью; при конфликте — суффикс.
- **Нет default export** в `index.ts` → авто-регистрация падает.
- **`interpolate` без `clamp`** → мерцание до старта и после конца.
- **Координаты вне канваса**: для full mode — `top > 1920` или `left > 1080` невидимо; для half mode — `top > 960`.
- **`React.CSSProperties` без импорта** → TS error. Импортируй `import type { CSSProperties } from 'react'`.
- **Эмодзи в Studio vs финальный рендер** — Studio показывает системные эмодзи macOS, а Remotion-бандл рендерит свои (часто Twemoji). Если для финального вида критично — реши сам: замени на SVG-примитив (не спрашивай пользователя).
